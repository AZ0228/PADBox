# PADBox team evaluator and optimizer

<!-- relay-plan
format: 1
defaults:
  preview: none
  agent: codex
  gate: auto

-->

PADBox can pool, shortlist and check a named team, but it cannot judge or build one. This plan fixes the validation the audit found unsound, makes the mechanics model describe game state, adds a deterministic simulator and evaluator, and only then adds search, dungeon profiles and the CLI.

## Background

The full brief is `docs/team-optimizer-brief.md`; each step names the sections it needs. The audit is `docs/team-builder-audit.md`, with issues `TB-01`…`TB-20` in `docs/team-builder-issues.md` and the old heuristics in `docs/team-builder-scoring.md` and `docs/team-builder-trace.json`. Treat the audit as a starting point and verify each claim against the code before acting on it. Where the brief and the decisions below differ, the decisions govern.

## Decisions

Settled for this plan. Hard-code them; do not build configuration for them.

- **Layers.** Layer A (mechanics, never selects teams) stays in `padbox.mechanics`. Layer B (evaluator, never searches) is the new package `padbox.evaluator`, with the simulator in `padbox.evaluator.sim`. Layer C (search) is the new package `padbox.optimizer`. Each layer has its own tests.
- **CLI.** The existing `padbox evaluate` is the recognition-accuracy command and stays unchanged. New commands live in a `padbox team` group: `team evaluate --team FILE`, `team optimize --leader ID [--helper ID] [--dungeon FILE] [--objective NAME]`, `team compare A B`. `pool`, `shortlist` and `check-team` keep working; `check-team` reports the new validation fields.
- **Card data.** The only source of truth is the pinned public PADDashFormation NA snapshot (2026-10-30) that `padbox sources sync` already uses. Regression cards are committed as small extracts in `tests/fixtures/cards/`, each with snapshot commit, monster ID and the raw skill fields used. No expectation may come from memory or wiki text.
- **Board.** 6×5 only. Other sizes are reported as unsupported.
- **Matching policy.** A deterministic greedy policy, documented in `docs/team-evaluator.md`. There is no orb-path solver, so every activation rate is labelled an approximation of what the policy achieves, not of human play.
- **Simulation defaults.** 10 turns, 1,000 Monte Carlo boards, seed 0. All three are flags, and every report records them.
- **Default objective.** `general`: exclude invalid teams, flag unresolved feasibility, then rank by activation consistency, survivability, damage and flexibility in that order. `farming`, `high-difficulty`, `boss-damage`, `consistent` and `fast` reorder or reweight the same component metrics. All formulas live in `docs/scoring-model.md`.
- **Search.** A staged beam search: broad candidate pool, constraint filter, cheap deterministic evaluation, a diverse beam (default width 200), full simulation of finalists only, then assists for the shortlist. No new optimization dependency.
- **Helpers.** Use an explicit `--helper`, or the user's own copies. Never assume a friend's helper exists.
- **Out of scope.** The Streamlit and live capture UI, authenticated game endpoints, real dungeon data (schema and the brief's example only), and claims of global optimality.

## Rules for every step

- Follow `AGENTS.md`: uv with Python 3.12, pytest and ruff. Run focused tests while working; the phase bundle runs the full suite once.
- Do not change scanning, recognition, inventory, snapshots or the existing `evaluate` command. No destructive SQLite migrations.
- Unknown is a value. Missing decoder output never means "no mechanic", and unknowns never silently pass or fail a hard requirement.
- Never weaken an existing test to make new behavior pass; change an assertion only when the audit shows it encoded a bug, and say so in the test.
- Commits carry no co-author or tool trailers.
